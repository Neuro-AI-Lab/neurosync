## Positive findings

- The mission-critical NED=0.20 catch-case (design §2, the VP-003 dominant-clause-vs-deleted-v3-phrase pair) was independently re-derived by hand, not trusted from the design: token Jaccard = 1/3 = 0.333 (< 0.5, confirms Jaccard alone would miss it), Levenshtein = 2, NED = 2/10 = 0.20 — exact match to the design's own table. The OR-combination (Jaccard ∨ NED) is load-bearing, confirmed correct.
- Retry-budget worst-case arithmetic (max 3 LLM calls/turn, additive not multiplicative across the 3 checked conditions because they share one loop and one budget) is logically sound; the min/max latency range citation is verified accurate (Issue 5).
- `_is_crisis_adjacent_turn`'s inputs (`session_state`, `safety_result`) are both already-licensed `DialogueInput` fields per the plan's own AVC-01 static allowlist (`docs/ai/validation_plan_f1f2_continuous.md` §6, `DialogueAgent` row) — no new classifier call, no persona/harness dependency, confirmed by direct code read. Consistent with "verification is external" / no harness-injection discipline.
- Fall-through-on-exhaustion (ship last attempt, log warning, never block) is sound and consistent with the codebase's existing single-retry precedent and this project's "no silent failures" convention.
- `docs/ai/prompts/dialogue/v4.system.md` confirmed byte-consistent with the design's claim of zero prompt-file changes (read directly; no BUG-030-iter-2/BUG-035 content present in the file, matching the design's "prompt files stay untouched, everything composed in code" claim).
- The design's own §5 "known limitation" disclosure (Korean questions without literal `?` may be under-detected) is appropriately hedged and honestly flagged rather than glossed over — good practice, consistent with this project's disclosure discipline.
- Design's explicit refusal to raise the retry budget above 2 without evidence, and its explicit routing of the "does the guard become the primary mechanism" question to EXP-018 data rather than guessing, is good pre-registration discipline.

## Ruling on the design's flagged open question (§8, de-escalation-turn boundary)

**Ruling: YES — include it, and more.** The design correctly identifies that a probe-concluding turn falls through to the ordinary round-robin branch (no `probe_instruction`) and asks whether it should count as crisis-adjacent. Issue 3 above provides direct, artifact-grounded evidence that the answer must be yes, and that the boundary needs to extend beyond just the de-escalation turn itself: in the actual BUG-035 reproduction session, turns 9 and 10 — several turns *after* the second probe cycle concluded at turn 6 — still carry `sentiment.polarity` of -0.85/-0.75 with despair 0.9/0.7, and both ship bare-question responses. A single-turn boundary extension would not have caught this. My ruling for EXP-018 pre-registration (see criteria below) is to score presence using the rubric's own sentiment-based population as the binding bar, not the code's runtime-signal population, and to report the delta between the two explicitly. Whether to also *widen the runtime guard itself* (e.g., a `turns-since-last-deescalation` counter) is an implementation decision for developer/orchestrator to consider for a future iteration — I flag it as recommended but do not mandate a specific mechanism, since that would exceed my review authority.

## Pre-registered EXP-018 acceptance criteria (exact, decidable)

Applies to any artifact whose `prompt_version` is the post-iteration-2 dialogue prompt (v4, unchanged file) with the guard code live. All criteria are reported per-session; never averaged into one composite pass/fail (per this project's established non-merging discipline, `rubric_bug030_acceptance.md` §9).

### A. Repetition bar (§2, mine to own — tightens Issue 2's ambiguity)

Computed over all non-excluded scored turns (exclude turn 0 greeting; exclude crisis-substituted turns; exclude turns whose `agent_response` fails JSON-schema parse):
1. Normalization is **pinned**: empathy clause = `_extract_leading_clause` output, surrounding whitespace stripped, **terminal punctuation included** (matches the production code; any rubric re-scoring must use the identical convention — resolves Issue 2's ambiguity by fiat for this pre-registration, but the rubric text itself still needs a corresponding correction, flagged above).
2. PASS(a): no phrase-family occurs more than 2 times among the session's empathy clauses (`_same_phrase_family`, Jaccard≥0.5 ∨ NED≤0.3).
3. PASS(b): zero occurrences of the same phrase-family across two turn-adjacent (consecutive, non-excluded) empathy clauses.
4. Automatic FAIL override: if any single phrase-family reaches ≥7 occurrences among the session's ≤10 scored turns (the VP-003 flat-repetition signature from `EXP-017`), the session FAILs (a) regardless of exact-string identity to a previously deleted phrase.
5. Session verdict: PASS only if both (a) and (b) hold. Report the max-phrase-family count and back-to-back count as supporting numbers, not substitutes for the PASS/FAIL bar.

### B. Presence bar (§4, BUG-035 — my ruling; CV reconciles the rubric-ownership half)

1. Telemetry check: zero turns ship (survive `fall_through`) with `presence_missing` as an unresolved final reason, among turns the **code** flags `crisis_adjacent=True`.
2. Rubric check (binding bar — supersedes 1 alone, per Issue 3): using the rubric's own sentiment-based qualifying-disclosure definition (§4 rules i/ii/iii) applied to every turn's `patient_message`/`sentiment` fields regardless of the code's `crisis_adjacent` flag, ≥0.90 of qualifying turns pair to a non-`NONE`, **genuinely affective** (not solely `겠`-substring-triggered — see criterion D) empathy clause in the immediately-following same-index `agent_response` (per the corrected same-index pairing, Issue 4), AND zero two-consecutive misses.
3. Coverage-delta report (mandatory, not optional): report `|rubric-qualifying-turn-count − code-crisis_adjacent-turn-count|` per session. A nonzero delta must be disclosed alongside any presence-bar verdict; criterion 1 alone (telemetry-only) **must never** be cited as sufficient evidence BUG-035 is resolved when this delta is nonzero.
4. De-escalation-boundary rule (my ruling, §8): the probe/SI-screen-concluding turn AND every subsequent turn whose `patient_message` still independently qualifies under rubric rule (i)/(ii)/(iii) count as crisis-adjacent for criterion 2, even when the code's `_is_crisis_adjacent_turn` returns `False`.
5. Session verdict: PASS only if criterion 2 holds. Criterion 1 is reported as a secondary/diagnostic number (guard efficacy), never the pass bar itself.

### C. SM regression bar

PASS iff assertion-identical to the `EXP-014` r2 / `EXP-017` baseline (10/11 cells PASS; `SM-08b`/`BUG-026` known-fail unchanged; safety v2 pin unchanged, re-verified pre/post-run). Any new failure not present in that baseline triggers the pre-registered bisection protocol (mirroring `validation_plan_f1f2_continuous.md` Appendix B) before any "regression-free" claim is reported; the guard's own diff (only `dialogue.py`'s `run()` + `_build_slot_context`'s empathy-block extraction) is bisected first among candidate causes.

### D. Telemetry sanity bar

PASS iff, on 100% of turns: `retry_count`, `retry_reasons`, `fall_through`, `retry_latency_ms`, `crisis_adjacent` are present; `retry_count > 0 ⟺ retry_latency_ms > 0`; `fall_through == True ⟹ retry_count == _MAX_REGENERATION_ATTEMPTS`; `len(retry_reasons) ≥ retry_count`. Any inconsistency invalidates the retry-rate/fall-through-rate/p95-latency claims for that run pending investigation.

### E. Marker false-positive spot-check (new, mine — addresses Issue 1)

Any EXP-018 report claiming the presence bar (B) PASSES must include a manual spot-check, by CV or critic, of every turn where `is_empathy=True` was decided **solely** by the bare `"겠"` marker (i.e., no other marker in `_EMPATHY_MARKERS` matched the same clause) — confirm each is genuinely affective, not a boilerplate procedural statement. Any confirmed false positive makes the presence-bar PASS provisional, pending a marker-set correction (routed back to developer, not resolved by this pre-registration).
