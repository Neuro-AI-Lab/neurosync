- 2026-07-08: Fourth occurrence, and a new sub-pattern — a test *labeled* as closing the gap that in fact documents it instead. REV-006 condition #3 (F2, "위험≠도메인") required a negative fixture + live probe. Developer shipped `test_f2_grounding.py::TestRiskNotDomainNegativeFixture`, whose own assertion (`counts[VERDICT_ACCEPTED] == 1`) proves a risk-laden utterance cited as domain evidence *passes* the whitelist — i.e. the "negative fixture" is an honest disclosure of the gap dressed as a closure, plus a companion string-presence check on the prompt text (same insufficient class as always). A test whose docstring says "demonstrates the boundary" rather than "prevents/rejects" is very likely the tell.
- 2026-07-08: Fifth occurrence, a new sub-sub-pattern — a *real* code-level fix (not prompt-only, not a mislabeled test) that is nonetheless incomplete relative to the project's own prior finding. Developer's v2 remediation for VAL-006/REV-008 added a genuine, code-enforced `_RISK_PHRASES` lexicon (`f2_grounding.py`) that correctly rejects the exact 2 quotes REV-008 quoted verbatim — real progress, not cosmetic. But REV-008 itself had already established a *broader* taxonomy (BUG-007/ADR-010's passive-SI/burdensomeness phrase family, "~9-10 of 13" quotes) as the more honest count than the strict literal one. The shipped lexicon and its regression fixture both silently narrowed back down to the 2 literal quotes, missing 2 whole paraphrase families ("짐이 되다" burdensomeness, "살아서 뭐하나" meaninglessness) that were sitting in the same already-reviewed artifact. Verified by deterministic replay of the lexicon's own substring-match logic against the real EXP-004 evidence quotes (not a live LLM call — fully reproducible by inspection) — 4/13 broader-taxonomy quotes still ship as accepted evidence today. Filed VAL-009 (REV-009). Lesson: when a project has already established a "broader/more honest taxonomy" finding in one review (here, REV-008), the very next remediation is the highest-risk point for silent scope-narrowing back to the literal/strict version — always replay the remediation against the SAME artifacts that produced the broader finding, not just the two headline quotes.
- 2026-07-08: also from REV-009 — when a remediation adds a code-level filter that can eliminate an LLM output's entire evidence set (a "cascade"), check whether elimination can trigger a *different*, pre-existing rollback criterion as an unintended side effect (here: risk-lexicon evidence-stripping → 0 domain candidates → the department that cited that domain becomes "orphan" → the unrelated, textually-unconditional "고아 department" rollback rule fires for a reason that is actually correct safety behavior, not department hallucination). This class of interaction is easy to miss because each mechanism was reviewed and ruled "sound" in isolation (REV-007 on both the whitelist and the orphan check) — the bug is only visible by tracing what happens when both fire on the same artifact.

- 2026-07-08 (REV-010): First time in this series the remediation held on independent re-verification. After BUG-014 (qa) added the two missing paraphrase-family stems VAL-009 flagged, EXP-005 (n=16, both arms, live) replayed the exact byte-identical inputs that triggered REV-008's original blocking finding — independent critic re-audit of all 42 accepted evidence quotes (not sampled, not accepted from the tracker's count) found 0/42 taxonomy hits, including an adversarial extension beyond the pre-registered list. Worth recording as a calibration point: a "fixed the two named quotes but check whether it generalizes" skepticism is still the right default (it caught the gap four times before), but it is not guaranteed to find something every time — when a remediation is replayed against the *same* artifacts that produced the broader finding (not new ones) and the filter also intercepts *additional* attempts beyond the originally-named quotes (here: 14 total interceptions vs. 2 originally named), that is meaningfully stronger evidence of genuine closure than a clean run on fresh, never-before-seen inputs would be.
- 2026-07-08 (REV-010): New adjacent pattern, first activation of a new mode/pipeline path tends to surface fresh, unrelated defects even when the safety-critical mechanism under test holds. RAG arm's first live run (EXP-005) had 0 risk-lexicon violations, but surfaced two new code defects neither REV-009's pre-run review nor any prior gate anticipated: a `source_id` format bug (model echoes a `chunk_id=` label from the prompt's own chunk-listing wording into the ID field it emits, causing ~29% over-rejection of genuine evidence) and an LLM-output-reliability failure (JSON truncation/schema-invalid) concentrated entirely on the one persona (VP-003) whose retrieval queries were most risk-topic-saturated. Neither is a validity violation of the thing being tested, but both would have gone unnoticed without opening every artifact's raw verdicts and stdout logs rather than trusting the aggregate counts. Lesson: on any "first activation" review (new arm, new mode, new integration point), budget time to read raw logs/verdicts even for dimensions the review isn't primarily about — defects cluster at first-activation boundaries.
- 2026-07-09 (REV-011): Sixth occurrence, a new sub-pattern distinct from prompt-vs-code and from scope-narrowing-within-one-channel — a genuinely correct, deterministic code-level mitigation that closes ONE channel completely (zero signal loss, verified by tracing that channel's compose function) while leaving sibling channels untouched that can carry the exact same problematic signal for the exact same high-risk case, because the underlying data-generating process makes that expected rather than a surprising edge case. VAL-010's mitigation removed `risk_assessment` from F2's Stage-1 retrieval queries (confirmed 100% risk-content by construction, no legitimate signal lost) — but VP-003's `chief_complaint`/`history_of_present_illness` (the two untouched channels) are themselves *designed* (persona spec's own expected-slot table) and already observed live (EXP-005) to carry the same passive-SI content. The fix is not wrong or incomplete in its own scope — it's that "the channel we could cleanly filter" and "the channel actually driving the bias for the hardest case" turned out to be different channels. Lesson: when a mitigation removes field X because X carries problem content, always check whether the *other* fields feeding the same downstream mechanism can carry equivalent problem content for the specific case that matters most — especially when that case's problem content is in its literal, designed presenting complaint (chief_complaint), not just in a derived/composed field. A clean per-field audit (does field X have legitimate content?) is not the same question as a system-level audit (can the bias re-enter through a sibling field for the worst-case input?).

- 2026-07-09 (REV-012, EXP-006): REV-011's §2 prediction (sibling-channel bias for VP-003's `chief_complaint`/HPI, VAL-010) reproduced live for a *second* consecutive batch, but the batch also independently proved the point moot for the moment: VP-003 RAG shipped zero evidence both runs (new schema-validation-failure mode, BUG-019, unrelated to VAL-010's mechanism), so the actual question ("does the sibling-channel bias contaminate shipped evidence?") is *still* untestable — two batches in a row have failed to produce the data point needed. Calibration note distinct from the enforcement-gap pattern itself: when a finding's resolution depends on a downstream artifact that keeps failing to materialize for unrelated reasons, resist the pull to call it "resolved-with-standing-condition" just because the mitigation code is correct and the audit was performed — "the check ran and found nothing to check" is not the same evidence class as "the check ran and found nothing wrong." Keep it open until the artifact actually exists to audit.
- 2026-07-09 (REV-012): Certification-disposition discipline, generalizable beyond this pattern — when an ADR/ruling lists N named conditions for lifting a status, do not average or round up ("2/3 met, mostly there"). Identify which condition is *load-bearing* (here: the one tied to the highest-scrutiny case the certification exists to police — VP-003) and gate on that one regardless of how many others passed. Also: a previously-clean case newly failing with the *same* failure signature as the case already under suspicion (here: VP-001/run1 failing identically to VP-003) is evidence *against* "isolated to the flagged case" — treat it as broadening the suspect set, not as noise to discount.

- 2026-07-09 (REV-013, PLAN-2026-W28-H Track B pre-implementation): Seventh occurrence, a new sub-pattern one level more subtle than prompt-vs-code — a genuinely code-level (not prompt-only) isolation design whose *invariants are scoped too narrowly by type*. Brainstorm's "AI 예상질환"/HPI-isolation design correctly used type-layer (`extra="forbid"`) + call-graph-layer (no function imports the new module AND constructs the three named schema types) + prompt-layer (no field to serialize) enforcement — a real advance over pure prompt instructions. But two freestanding, already-existing generic channels reach the exact same downstream LLM-prompt sink (`_build_user_content`) the design protects, and neither is named by any of the three layers: `AgentInput.extra: dict[str, Any]` (a legitimately-declared field every agent input inherits — `extra="forbid"` governs *undeclared* kwargs, not this one) and `state.conversation_history` (raw chat-turn text, already serialized verbatim into the same prompt, populated by ordinary turn-handling code that never needs to import the new module or construct any of the three named schema types). Ruled INADEQUATE-with-named-gap rather than approved-as-is. Lesson: when a design claims "structurally impossible by construction" via type/import-graph invariants scoped to N named schema types, always ask whether any *other*, already-existing field on those same objects (especially a generic dict/free-text bucket) reaches the identical downstream sink the invariants are meant to protect — a call-graph test scoped to "imports module X AND constructs type Y" cannot see a leak that flows through a plain-string/plain-dict field Y already has, populated by code that imports neither.

- 2026-07-09 (REV-015, EXP-008): Capstone of the REV-008→REV-010→REV-012→REV-014→REV-015 RAG-arm certification arc — the load-bearing condition named in REV-012 (VP-003 RAG output reliability, tracked as BUG-019) was root-caused (a `source_type` field-name collision, same conceptual class as BUG-016 but a different field) and fixed with a narrow, deterministic, pre-validation regex coercion; the very next live batch (n=2 VP-003 + n=2 VP-001, applying REV-014's own pre-registered interpretable-vs-legitimate-0-candidate rule) came back 4/4 clean and the arm was lifted in full. Calibration note on evidentiary sufficiency, complementing REV-012's "gate on the load-bearing condition" note above: a single clean n=2 batch is normally thin evidence in this project (see VAL-002/004/008's repeated single-batch-miscount pattern), but it is not automatically thin when the fix being confirmed is a deterministic code-level mechanism (not a prompt/statistical change) AND the batch itself contains a within-batch replication of the exact trigger condition the root-cause analysis named (here: VP-001 cited `qa:`-table chunks as evidence 6+ times across its two runs with zero collisions, independently corroborating the fix beyond the headline "0 failures" count). When judging whether a single post-fix batch is enough to lift a standing block, check for (a) mechanism-level understanding of the fix (not just "it worked this time") and (b) whether the batch's own composition happens to re-exercise the specific failure trigger multiple times, not just whether N runs passed in aggregate.

- 2026-07-09 (REV-017, EXP-009/EXP-010): Eighth occurrence, a new sub-pattern one level more subtle than REV-013's type-scoping gap — a genuinely code-level, mutation-tested filter (VAL-011's risk-lexicon check on `AIPredictedDiseaseCandidate.quote`) whose *check-target* is narrower than its own binding condition's text. ADR-020 condition 1 said "any candidate whose sole matched **chunk** is risk-lexicon-flagged is DROPPED"; the shipped code checks only a deterministic ±40-char extracted-quote window around the matched *symptom* term, never the full chunk — a window whose position is chosen for provenance-legibility, not risk-awareness, so it can and does miss risk content sitting >40 chars away in a longer chunk. Reproduced live twice (same persona, two different k values) on exactly the chunk IDs (`case_card:664`, `case_card:563`) the sibling `domain_candidates` pipeline — checking the LLM's own accountable quote selection, not a blind window — independently rejected in the same run. The shipped regression test (`TestVal011...`) used a ~35-char single-sentence fixture where the matched term is *necessarily* within 40 chars of the risk phrase, so it could not have caught this; qa's mutation-testing verified the test was load-bearing on the fixture it had, which is a different claim from "the fixture's geometry matches the real failure geometry." Lesson, generalizable: when a deterministic extraction/windowing step sits between a source of risk and the actual check (here: chunk text → extracted quote → lexicon check), always ask whether the shipped test fixture's *size/shape* is representative of live inputs (real corpus chunks run to several sentences) or is a toy string that structurally cannot separate "term of interest" from "risk phrase" by more than the window width — a short-string fixture will pass regardless of whether the windowing logic is safe, so a passing mutation-tested test on a short fixture is much weaker evidence than the same test on a fixture sized like production data. Also reinforces REV-012's "gate on the load-bearing condition" note: the binding condition's own wording ("chunk" vs "quote") should have been checked literally against the implementation before accepting closure.

When resolving this failure class in review responses to developer, quoting the binding text verbatim (not paraphrasing) appears to correlate with a correctly-scoped fix.

- 2026-07-10 (REV-019, pre-run gate for EXP-012): Adjacent but distinct calibration note, not the enforcement-gap pattern itself — "genuinely new live LLM calls" language in this project's EXP entries has, across 7 consecutive RAG/populated-path batches (EXP-005 through EXP-011), only ever meant "new Solar Pro3 sampling given identical input text," never "new input content." Every one of those batches reused the SAME ~8 F1-generated `conversation.json` files from 2026-07-07, cross-verified byte-identical by SHA256 batch after batch. REV-017's blocking finding and REV-018's fix-confirmation were both derived entirely from that one fixed input set. When a claim says "genuinely new live calls, not artifact replay," always check which stage the novelty applies to — a downstream stage (F2) can be genuinely re-sampled while its upstream input (F1's conversation text) stays frozen for many consecutive "independent" batches, silently narrowing the certification's real empirical coverage to one input distribution. Ask explicitly, for any certification resting on repeated "batch" language: has any dimension of the *input*, not just the *call*, ever actually varied?

- 2026-07-10 (REV-022, plan-stage review of PLAN-2026-W28-O's RAG trigger-policy A/B design): Ninth occurrence, and the first at plan stage (before any code exists) rather than post-implementation — both proposed mitigations for VAL-010 (still-open, 7-batch-reproduced) target a channel this project already proved, by name, is *not* the residual problem. Policy A's fallback excludes "Safety-Probe/SI-screen-adjacent turns"; Policy B's judge hard-excludes the `risk_assessment` slot. But REV-011 §2 already established explicitly that VAL-010's unaddressed channel is `chief_complaint`/history_of_present_illness — the persona's own designed presenting complaint, not probe/SI-screen content and not `risk_assessment` (both already excluded from the *original* mitigation and never the residual problem). Lesson: when a plan proposes a *new* mitigation for a standing, already-diagnosed finding, check the new mitigation's excluded/protected scope against the *specific channel* the prior finding named as residual — not against the general failure category. A design can look like a genuine, on-topic response to "risk content biasing retrieval" while actually re-solving an already-solved sub-problem and leaving the diagnosed one untouched, especially when the new design is proposed by a different specialist (brainstorm/orchestrator here) than the one who wrote the original finding (critic, REV-011) and doesn't re-read the finding's own channel-level specificity, only its headline. Catching this required tracing A5's two policy designs against REV-011 §2's literal sentence, not just against "does this address VAL-010" as a yes/no.

- 2026-07-11 (REV-024, W4 gate for PLAN-2026-W28-Q): Closure of the ninth occurrence, on the *first* redesign pass — confirms REV-018's lesson generalizes from post-implementation bug-fixes to plan/design-stage fixes too. Developer's single-choke-point `apply_risk_lexicon_filter` (`rag_trigger.py`) targets the exact channel REV-011 §2 named as residual (`chief_complaint`/HPI text itself, filtered for both policy arms including the previously-unfiltered default path), not the already-excluded turn-class/`risk_assessment` channels the original designs mistakenly re-solved. The shipped tests include a purpose-built "VP-003-run2 shape" fixture that specifically defeats turn-exclusion-only mitigations (risky text arrives via the primary slot path on the SAME turn that is also the probe-trigger turn) — evidence the fix was built by re-reading the finding's literal channel-level sentence, not just its headline, mirroring REV-018's own successful pattern. **New, distinct calibration note from the same review, worth tracking as its own watch-item:** even a correctly-targeted architectural redesign can carry an adjacent, unrelated "computed but never persisted" gap — the judge agent (`rag_trigger_judge.py`) correctly computes real per-call `latency_ms`, but the trigger-decision layer's persisted audit dict (`rag_trigger.py`'s `judge_output` literal) silently omits it, and the regression test asserting that dict's shape encoded the omission rather than catching it (the fixture's expected-value dict simply didn't include the field either). This is a different failure class from mitigation-target-mismatch: not "which channel is checked" but "which of an already-correct computation's fields survive to the artifact a later measurement depends on." When a new field is added to an agent's output for a specifically-named downstream purpose (here: Criterion 3's latency threshold), trace it all the way to the persisted artifact dict-literal, not just to the agent's own return statement — a dict literal that lists fields by name (`{"retrieve": ..., "query": ..., "reason_summary": ...}`) is exactly where a real field silently drops out and no type-checker catches it (a plain `dict[str, Any]`, not a Pydantic model, was used for this specific persistence layer).

**Why:** Whenever this project's design puts a structural/safety guarantee entirely in prompt wording (a "must not" instruction, a self-check line, an assertion the model is trusted to honor) without an equivalent code-level check, the small Korean LLMs in use here eventually violate it under live conditions. Prompt-text assertions and string-presence offline tests (checking the instruction *exists* in the prompt) do not test whether the model *obeys* it — that requires a live/fixture behavioral test or a runtime code-level backstop.

**How to apply:** When reviewing any plan or prompt design that claims a hard guarantee (fabrication=0, no false crisis, no leakage of X into Y), always ask: (1) is this enforced by prompt wording alone, or is there a code-level check operating on the actual output content? (2) if prompt-only, is there at least a live/fixture test that exercises the specific failure mode (not just a text-presence assertion that the instruction exists)? Flag as major (not necessarily blocking at plan stage, since these are cheap to close before implementation) whenever a central validity claim rests on prompt-only enforcement with no live behavioral test — this project's own history (BUG-007, BUG-010) shows these gaps do materialize, not just theoretically could.
